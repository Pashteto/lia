# Мобильные операторы РФ: обрыв TLS на 443 — диагностика и план решения

**Дата:** 2026-08-14
**Статус:** диагностика не завершена — нужен прогон тестов с мобильной сети
**Тикет хостера:** №96742 (услуга ID 164438, IP 193.32.188.7, нода ru215)
**Затронуто:** `presence.tarski.ru`, `api.presence.tarski.ru` (прод Lia)

---

## 1. Симптом

Сайт стабильно не открывается у пользователей мобильного интернета российских операторов
(МТС, МегаФон, Билайн, Tele2). С проводных подключений и Wi-Fi работает нормально.

Картина по диагностике:

- TCP-соединение на 80 и 443 устанавливается **всегда**;
- HTTP (порт 80) стабильно отвечает 301;
- HTTPS: соединение установлено, ClientHello отправлен, дальше **RST (`SSL_ERROR_SYSCALL`)**;
- другие сайты с того же телефона в тот же момент открываются нормально.

На сервере проблем нет: nginx active, load average 0.30, uptime 49 дней, за сутки 809 ответов 200
и практически нет ошибок, в iptables нет DROP-правил, fail2ban настроен только на SSH.

Хостер подтвердил доступность сервера и сообщил:

объективно, без участия хостера.

## 3. Три гипотезы

Симптом «TCP ок, HTTP:80 ок, RST сразу после ClientHello» имеет три разные причины,
и **две из трёх переездом не лечатся**.

| # | Гипотеза | Признак | Поможет ли переезд |
|---|---|---|---|
| A | ТСПУ режет по **SNI/домену** | падает только с `-servername presence.tarski.ru`; с чужим SNI на тот же IP хендшейк проходит | ❌ бесполезно — лечится сменой домена |
| B | **PMTU-блэкхол** на мобильной сети | ClientHello (маленький) уходит, ServerHello + цепочка сертификатов (несколько КБ) не пролезает; ICMP frag-needed зарезан | ❌ бесполезно — лечится MSS-клампом на сервере, бесплатно |
| C | IP / подсеть **193.32.188.0/24** в блок-листе | падает с любым SNI и по голому IP; у соседних IP хостера то же самое | ✅ да, но достаточно **сменить IP**, а не хостинг |

Про гипотезу B: она хорошо объясняет всю картину. Клиент шлёт маленький ClientHello — пролезает.
Сервер отвечает большим ServerHello + сертификатами — на мобильном MTU 1400–1420 пакет дропается,
соединение виснет и рвётся в RST. HTTP:80 с крошечным 301 при этом работает идеально.

## 4. DNS-факты (проверено 2026-08-14)

```
tarski.ru              → 185.199.108-111.153   GitHub Pages
www.tarski.ru          → anton-gorokhovatsky.github.io → те же
presence.tarski.ru     → 193.32.188.7          наш VDS (vds-ru215)
api.presence.tarski.ru → 193.32.188.7          наш VDS
```

**Важно:** «`tarski.ru` с мобильного работает отлично» — НЕ доказательство того, что домен чистый.
Корневой домен живёт на GitHub Pages: другой IP, другой хостер, другой сертификат, другой сетевой путь.
Прямое сравнение невалидно.

Косвенно это **сдвигает вероятность к гипотезе C**: та же доменная зона с мобильных работает,
ломается только то, что стоит на `193.32.188.7`. Плюс ТСПУ редко режет по SNI конкретный поддомен
маленького сайта про мероприятия, а дешёвый VDS-/24 с соседями-VPN в блок-листе — сюжет массовый.

## 5. Тесты (~30 минут, бесплатно)

Прогонять **с мобильной сети**. Самый удобный способ: раздать интернет с телефона на Mac по hotspot
и выполнять команды из обычного терминала.

### 5.1. Ключевой тест — SNI (решает A vs C)

Отправляем на наш IP чужое имя. Несовпадение сертификата не важно — важно только,
доходит ли хендшейк до ServerHello.

```bash
# 1. наше имя на наш IP — ожидаем поломку
openssl s_client -connect 193.32.188.7:443 -servername presence.tarski.ru -tls1_2 -brief </dev/null

# 2. ЧУЖОЕ имя на наш IP
openssl s_client -connect 193.32.188.7:443 -servername tarski.ru -tls1_2 -brief </dev/null
openssl s_client -connect 193.32.188.7:443 -servername ya.ru      -tls1_2 -brief </dev/null

# 3. без SNI вообще
openssl s_client -connect 193.32.188.7:443 -tls1_2 -brief </dev/null

# 4. наше имя на ЧУЖОЙ IP (GitHub) — контроль, что имя само по себе не токсично
curl -vk --resolve presence.tarski.ru:443:185.199.108.153 https://presence.tarski.ru/ 2>&1 | head -20
```

Чтение результата:

- **(2) работает, (1) падает** → гипотеза **A**, блок по SNI/домену. Переезд бесполезен,
  лечится сменой домена (отдельная зона под проект).
- **(1) и (2) падают одинаково** → гипотеза **C**, блок по IP. Смена IP / переезд решает проблему.
- **всё падает, включая (4)** → гипотеза **B**, MTU. Чиним на сервере бесплатно.

### 5.2. MTU (проверяет B)

```bash
ping -D -s 1472 193.32.188.7   # 1500 байт
ping -D -s 1372 193.32.188.7   # 1400 байт
```

1472 не проходит, 1372 проходит → почти наверняка **B**. Фикс на сервере (обратимый, минута):

```bash
iptables -t mangle -A POSTROUTING -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
# или жёстко: -j TCPMSS --set-mss 1360
```

### 5.3. Периодичность отказов

Хостер говорит «периодически», в тикете было «стабильно» — надо померить процент.

```bash
for i in $(seq 1 30); do
  curl -sS -o /dev/null -w "%{http_code} tcp=%{time_connect} tls=%{time_appconnect}\n" \
    https://presence.tarski.ru/ || echo FAIL
done
```

- Ровные 100% отказов → статичный блок-лист.
- 30–60% → DPI-эвристика или гонка с MTU.

### 5.4. Реестр РКН

Проверить `193.32.188.7` и `193.32.188.0/24` через rublacklist.net и списки zapret-info.
Две минуты, закрывает гипотезу C документально.

### 5.5. Данные для тикета (хостер просил)

- домены: `presence.tarski.ru`, `api.presence.tarski.ru`;
- 5–10 меток времени неудачных попыток + часовой пояс (MSK);

## 6. План действий по результатам

### Если A (блок по SNI/домену)

Переезд не нужен и не поможет. Регистрируем отдельную зону под проект, переносим
`presence.*` на новое имя, редирект со старого. Учесть: `NEXT_PUBLIC_API_URL` в build-args
фронтенда, CORS/allowed origins на бэкенде, сертификаты Let's Encrypt, ссылки в письмах SendPulse.

### Если B (MTU)

MSS-кламп на сервере (п. 5.2), перепроверить с мобильной сети, зафиксировать правило в
persistent iptables / compose. Стоимость — ноль, переезд не нужен.

### Если C (блок по IP) — сейчас наиболее вероятно

По возрастанию цены:

1. **Запросить другой IP из другой подсети** у того же хостера в тикете №96742.
   Часто бесплатно, миграция не нужна — только DNS. Плюс это прямая проверка гипотезы.
2. Не дали / не помогло — **проверить крупное RU-облако до переезда**: Selectel, Timeweb Cloud,
   Yandex Cloud. Поднять VDS на час (~300 ₽), повесить тестовый поддомен с Let's Encrypt,
   прогнать тесты п. 5.1 с телефона. Их подсети практически не попадают под блок —
   слишком большой сопутствующий ущерб для ТСПУ. У дешёвых VDS-хостеров соседи по /24 —
   главный источник этой проблемы.
3. Только после зелёного теста — миграция всего стека: docker-compose (4 файла) + volume
   `lia_uploads` + дамп `lia_prod` + `.env.prod` + сертификаты. См. раннбуки в
   `docs/superpowers/runbooks/`.

### Чего НЕ делать

- **Cloudflare перед сайтом** — в РФ сам деградирован мобильными операторами, сделает хуже.
- Мигрировать до прогона тестов — два сценария из трёх переездом не лечатся, деньги и день уйдут впустую.

## 7. Открытые вопросы

- Тесты с мобильной сети не прогнаны (нужен hotspot или телефон с Termux).
- Сетевая линия хостера не вернулась с логами фильтрующего оборудования по 443.
- Не измерен реальный процент отказов — «стабильно» vs «периодически» расходится
  между нашим и их описанием.

## 9. Переименование в `p.tarski.ru` / `api.tarski.ru` — сделано, НЕ помогло (2026-09-02)

Развёрнуто полностью: A-записи `p` и `api` → 193.32.188.7 (nic.ru, зона опубликована),
сертификат Let's Encrypt на оба имени, nginx-блок `tarski-p`, второй фронт-контейнер
`lia-frontend-ptarski` (:3003, собран с `NEXT_PUBLIC_API_URL=https://api.tarski.ru`),
бэкенд: `HTTP_CORS_ALLOWED_ORIGINS` = presence + p, `STORAGE_PUBLIC_BASE` → `api.tarski.ru`.

С iPhone имя **открылось один раз** (access.log 04:38:14, CriOS/152, все чанки 200),
затем перестало открываться и с телефона, и с домашнего интернета.

### Решающий эксперимент — SNI против нашего IP

`curl --resolve <имя>:443:193.32.188.7` с домашнего маршрута:

| SNI | Назначение | Результат |
|---|---|---|
| `example.com` | 193.32.188.7 | ✅ handshake 0.15 с |
| `tarski.ru` (корень) | 193.32.188.7 | ✅ handshake 0.05 с |
| `www.tarski.ru` | 193.32.188.7 | ❌ дроп |
| `zzz9x.tarski.ru` (не существует) | 193.32.188.7 | ❌ дроп |
| `p.tarski.ru` | 193.32.188.7 | ❌ дроп |
| `api.tarski.ru` | 193.32.188.7 | ❌ дроп |
| `presence.tarski.ru` | 193.32.188.7 | ❌ дроп |
| `p.tarski.ru` | 185.199.108.153 (GH Pages) | ✅ handshake, 404 |
| `presence.tarski.ru` | 185.199.108.153 | ✅ handshake, 404 |

**Правило ТСПУ:** дроп ClientHello по паре «назначение 193.32.188.7 + SNI вида
`<label>.tarski.ru`». Не IP как таковой (example.com и корневой `tarski.ru` на тот же
IP проходят), не имя как таковое (те же имена на IP GitHub проходят), не MTU, не порт
(TCP-хендшейк на 443 устанавливается, HTTP:80 отдаёт 301 стабильно).

### Правило маршрутозависимо

Одновременно с дропом на домашнем маршруте `https://p.tarski.ru` и
`https://presence.tarski.ru` отдают 200:
- с oracle-1 (зарубежный IP) — appconnect ~1.0 с;
- с vdska 185.5.75.80 (**другой российский** IP, ДЦ) — appconnect ~0.4 с.

То есть режет ТСПУ на конкретных маршрутах (потребительская «последняя миля»),
а не магистраль целиком. Сайт при этом живой: в access.log идут 200 от посторонних
клиентов, сервер здоров (uptime 68 дней, load 0.14, nginx ok, диск 75%).

### Вывод

- Гипотеза **A уточнена**: режут не конкретное имя, а **всю зону `*.tarski.ru`
  в связке с нашим IP**. Смена поддомена внутри зоны бесполезна — это доказано
  экспериментом, а не рассуждением.
- Лечится **одним из двух**, оба проверяемы дёшево:
  1. **другой домен** (отдельная зона) на тот же IP — прямо подтверждено тем, что
     SNI `example.com` на 193.32.188.7 проходит;
  2. **другой IP** под теми же именами — правило привязано к паре, но нет гарантии,
     что новый IP не переразметят.
  Вариант 1 дешевле и опирается на прямое измерение. Вариант 2 требует покупки IP
  у хостера и повторной проверки.
- Что оставить: `p.tarski.ru` / `api.tarski.ru` поднимать обратно не нужно, но и
  сносить смысла нет — с проводных/зарубежных маршрутов работают.

### Что НЕ доделано

- `PUBLIC_BASE_URL` намеренно не переключался на `p.tarski.ru` — ссылки в письмах
  остались на `presence.tarski.ru`.
- Изменения бэкенда живут только на боксе; в репозитории `docker-compose.prod.yml`
  ещё со старыми значениями. Бэкап на боксе: `docker-compose.prod.yml.bak-20260902`.
