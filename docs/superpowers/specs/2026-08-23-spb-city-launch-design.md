# СПб: запуск второго города — дизайн

**Дата:** 2026-08-23
**Статус:** утверждён в брейншторме, ждёт ревью спеки
**Скоуп:** полный запуск СПб — от модели данных до открытия города публично (контентный трек включён).

## Контекст

Сегодня города как понятия в системе нет: вся платформа неявно московская.
В шапке живёт переключатель `CityControl` с одним рабочим пунктом «Москва» и
задизейбленным «Санкт-Петербург — Скоро». После QA 14.08 весь городской
копирайт централизован в `frontend/lib/city.ts` (код, падежи, центр карты,
`available`), но:

- в таблицах `events` и `venues` нет колонки города;
- `ListFilter` (`backend/internal/events/repository.go`) не умеет фильтровать по городу;
- `CURRENT_CITY = CITIES[0]` — константа, клик по городу ничего не переключает;
- каталог площадок в проде (174 шт.) целиком московский;
- питерских событий нет.

## Решения, принятые в брейншторме

1. **Скоуп — полный запуск**: тех-механика + сид площадок + наполнение событиями + публичное открытие.
2. **Выбор города пользователя**: cookie `lia_city` (SSR-читаемая) + override `?city=` на публичных страницах. Без перестройки роутинга.
3. **Город в модели данных**: и на `venues`, и на `events` (денормализовано; при выборе площадки событие наследует её город).
4. **Источники контента СПб**: все три — импорт с whitelist-платформ (внешняя регистрация), живые организаторы (аутрич), редакционная курация.
5. **Механизм открытия города**: вариант А — доступность города (`available`) — серверная runtime-настройка, отдаваемая `GET /api/v1/cities`. Список городов — захардкоженные константы бэкенда (`msk`, `spb`); таблица `cities` в БД — YAGNI. Фронтовый `lib/city.ts` остаётся источником локализации (падежи, центры карт).

## 1. Модель данных — миграция 000027

- `venues.city text NOT NULL DEFAULT 'msk'`; backfill всех существующих строк значением `'msk'`.
  Индекс поиска площадок становится `(city, lower(name))` (заменяет `venue_name_lower_idx`);
  расширения из миграции 000022 (trigram и пр.) продолжают работать поверх.
- `events.city text NOT NULL DEFAULT 'msk'`; backfill `'msk'`. Индекс под публичный листинг: `(city, starts_at)`.
- Код города — slug латиницей: `msk`, `spb` (НЕ «МСК»). Валидация на бэкенде
  по белому списку констант; невалидный город → 400.
- Down-миграция дропает колонки и возвращает старый индекс.

### Наследование города событием

- Событие с площадкой (`venue_id` задан): `events.city` копируется из `venues.city`
  при создании и при смене площадки в PATCH. Переопределить нельзя — попытка
  передать `city`, отличный от города площадки, → 400.
- Событие без площадки (внешние, черновики без места): организатор передаёт
  `city` явно; дефолт `msk`.

## 2. Backend API

### Фильтр по городу

- `ListFilter` получает поле `City string` (пустое = без ограничения, как остальные поля).
- Хендлеры публичных выборок принимают `?city=<slug>`:
  публичный листинг событий, поиск, события для карты, публичный календарь.
- **Дефолт при отсутствии параметра — `msk`**: старые клиенты и закешированные
  страницы не меняют поведения; питерские события не «протекают» в московскую афишу.
- Личные выборки (`/me/practices`, `/me/applications`, `/me/calendar`,
  «Мои события» организатора, админские/модерационные списки) город
  НЕ фильтруют — там пользователь видит всё своё независимо от выбранного города.

### Площадки

- `GET /api/v1/venues` (поиск при создании события): параметр `city` обязателен;
  ILIKE-поиск ограничивается городом.
- Яндекс.Places-подсказки: запрос к Places ограничивается bbox выбранного города
  (bbox-константы рядом с городскими константами бэкенда).

### Города

- Новый эндпоинт `GET /api/v1/cities` → `[{ "code": "msk", "available": true }, { "code": "spb", "available": false }]`.
  Публичный, без авторизации, кешируемый.
- `available` для `spb` читается из env `CITY_SPB_AVAILABLE` (bool, дефолт false),
  объявленной в compose по образцу `auto_verify_all` — открытие города не требует
  пересборки образа, только правку env + recreate контейнера.

## 3. Frontend

### Состояние выбора

- Cookie `lia_city` (значение — slug), читается в SSR (layout) и на клиенте.
- На публичных страницах (лента, карта) `?city=spb` переопределяет cookie и
  записывает её — шаримые ссылки работают.
- `CURRENT_CITY` заменяется на `getCity()` для серверных компонентов и
  city-контекст для клиентских. `lib/city.ts` сохраняет `CITIES` c локализацией
  и центрами; поле `available` больше не захардкожено — приходит из `GET /api/v1/cities`
  (SSR-фетч в layout, передаётся в контекст).
- Неизвестное/недоступное значение cookie → тихий откат на `msk`.

### Компоненты

- `CityControl`: клик по доступному городу = записать cookie + `router.refresh()`.
  Недоступные города — как сейчас, «Скоро», но признак серверный.
- Лента (`DiscoveryFeed`), карта (`MapBrowse` — центр!), тайтл в layout,
  подпись на логине уже параметризованы объектом `City` — переезжают автоматически.
- Форма создания/редактирования события: селектор города, видимый только когда
  доступных городов больше одного; поиск площадок передаёт выбранный город.
- Запросы ленты/карты/поиска/календаря добавляют `city=<выбранный>`.

## 4. Контент (после тех-готовности, до открытия)

1. **Сид площадок СПб**: переиспользовать pipeline seed+geocode из `docs/research`;
   первая партия ~50–80 ключевых площадок (Эрмитаж, Русский музей, Главный штаб,
   Манеж, Севкабель Порт, Новая Голландия, Планетарий №1, Anna Nova и т.п.),
   все с `city='spb'`.
2. **Импорт whitelist-платформ**: подборка питерских событий с TimePad и др.
   через существующий механизм внешней регистрации. Учесть: такие события
   попадают в `pending_review` — закладываем модерацию партии.
3. **Редакция + организаторы**: редакционный аккаунт-организатор для ручной
   курации афиши СПб; параллельно аутрич живым питерским организаторам (вне кода).

**Критерий открытия:** включаем `spb.available=true`, когда в афише СПб
≥15 живых будущих событий.

## 5. Тестирование

- Backend unit: фильтрация `ListFilter.City`; наследование города от площадки
  (создание + смена площадки в PATCH + конфликт → 400); валидация slug;
  `GET /api/v1/cities` с выключенным/включённым флагом; venue-поиск требует city.
- Frontend unit: расширить `city.test.ts` / `city-control.test.tsx` —
  переключение пишет cookie, недоступный город не кликается, `?city=` override,
  откат на `msk` при мусорной cookie.
- Ручная проверка на проде после деплоя шага 1: московская афиша не изменилась,
  `?city=spb` даёт пустую ленту с корректным копирайтом и центром карты СПб.

## 6. Деплой — два шага

1. **Тех-деплой (ничего не меняется для пользователей):** миграция 000027 →
   бэкенд → фронт. СПб остаётся «Скоро» (`CITY_SPB_AVAILABLE` выключен).
   Стандартная схема: build-on-Mac → save|ssh|load, тег `:latest` перед
   recreate, rollback-теги, `.sql` scp на бокс, прогон по раннбуку.
2. **Открытие:** после наполнения контентом (критерий ≥15 событий) —
   включение настройки + `up -d` без пересборки. Откат = выключить настройку.

## Вне скоупа

- Третий и последующие города (дизайн их не блокирует: добавление = константа
  бэкенда + запись в `CITIES` + сид площадок).
- Таблица `cities` в БД и админка городов.
- Гео-определение города пользователя по IP.
- URL-сегменты `/spb/...` и SEO-раздача городских страниц.
- Питерские справочники метро/районов (поля свободный текст — ничего не блокируют).
