## Зачем

Месячный лимит был только глобальным: одно число на всех, меняется правкой
`EVENTS_MONTHLY_LIMIT` на боксе с пересозданием контейнера. «Редакция PRESENCE»
заводит импорт пачками и упиралась в него каждый раз — за сентябрь лимит
поднимали и возвращали трижды.

Снятие лимита обнажило вторую дыру: **дедупликации у нас не было нигде**. Сборщики
читают `state.json`, но в него никто не пишет — README просит дописывать руками, а
у TimePad файл вообще был пуст, из-за чего прогон 24.09 предложил два уже
опубликованных события. На бэкенде уникальности на `events` не было вовсе, и
единственным фактическим тормозом против повторного импорта был 429 от квоты —
ровно то, что мы и убирали.

## Что сделано

**Миграция 30** — `organizers.monthly_event_limit`, зеркало `daily_event_limit`
из миграции 24: `NULL` = глобальный дефолт, `0` = без капа.

**Миграция 31** — частичный уникальный индекс
`events (source_url, starts_at) WHERE source_url <> ''`.
Ключ — **пара**, а не один `source_url`: один пост регулярно анонсирует серию
(«ближайшие корайтинги: 3, 17, 31 октября»), и это разные события из одного
источника. Индекс запрещает ровно повтор — тот же источник на то же время.
Частичный, чтобы события организаторов о своих площадках и 87 импортированных до
миграции 29 сохранили пустой `source_url` без коллизий.

**Домен.** `MonthlyLimitLookup` + `monthlyLimitFor` по образцу дневного, включая
падение на дефолт при ошибке лукапа. Месячный отказ стал типизированным
`QuotaError{Period: "month"}`, и `quotaMessage` строит русский текст из реального
числа — при лимите 10 формулировка не изменилась ни на символ.

**Ручка.** `POST /api/v1/admin/organizers/{id}/monthly-limit`.
Тело `{"limit": 0}` / `{"limit": null}`. Общее тело двух лимитных ручек вынесено в
`setEventLimit`.

**Перевод ошибки.** Нарушение уникальности ловится на краю репозитория
(`isDuplicateSource`, SQLSTATE 23505 + имя индекса) и превращается в
`ErrInvalidInput` → HTTP 400 «это событие уже заведено из того же источника»,
а не 503.

**Сборщик** (`4f12521`, отдельная история). `tg-ingest` клал ссылку на сам пост в
`external_registration_url`, когда в анонсе не было ссылки регистрации. `t.me` не в
белом списке платформ → `applyExternalURLPolicy` уводил событие в `pending_review`
при публикации. Именно поэтому все восемь телеграм-импортов тихо осели в модерации.
Теперь: нет ссылки регистрации → `signup_mode: "open"`, пусто; ссылка на канал
живёт в `source_url`.

## Порядок выкатки (как делалось)

1. Проверка на повторы **до** миграции — иначе `CREATE UNIQUE INDEX` упадёт:
   ```sql
   SELECT source_url, starts_at, count(*) FROM events
   WHERE source_url <> '' GROUP BY 1,2 HAVING count(*) > 1;
   ```
   Было чисто: 125 событий, 7 с источником, повторов нет.
2. `git worktree add /tmp/deploy-monthly <sha>`; в worktree нет сгенерированного
   кода — `make generate-api` + копия `protocols/userservice/*.pb.go` из основного дерева.
3. `docker build --platform linux/amd64 -t backend-app:monthly-r1 .`
4. **Метка отката — с работающего образа, ДО `docker load`:**
   `docker tag <running-image-id> backend-app:rollback-monthly-20260924`
5. `docker save ... | ssh ... docker load`
6. `scp` четырёх `.sql` в `/opt/lia/backend/db/migrations/`
7. `pg_dump -Fc` в `/opt/lia/backup-pre-monthly-20260924.dump`
8. `docker compose --env-file .env.prod -f docker-compose.yml -f docker-compose.prod.yml \
   -f docker-compose.gateguard.yml -f docker-compose.monitoring.yml run --rm migrate`
9. **`docker tag backend-app:monthly-r1 backend-app:latest`** — без этого пересоздание
   молча поднимет старый образ.
10. `... up -d --no-build --force-recreate app`
11. Прибрать: `docker builder prune -f`, `docker image prune -f`, откатных меток ≤3.

## Проверка на живом проде

- `схема=31 dirty=false`, колонка `monthly_event_limit` и индекс
  `events_source_url_starts_at_idx` на месте.
- В логе: `events monthly limit = 10 (per-organizer override wired)`.
- `POST .../monthly-limit` без токена → 401 (ручка есть), соседний несуществующий
  путь → 404.
- «Редакции PRESENCE» проставлен `monthly_event_limit = 0` → пять событий завелись
  подряд со статусом `published`, без единого 429.
- Повторная отправка того же `source_url` на то же время → **400**, не 503.
  Контроль «та же ссылка, другая дата» вживую НЕ проверялся (создал бы мусорное
  событие) — только юнит-тестами и определением индекса.

## Грабли этого захода

1. **`repository_test.go` помечен `//go:build integration`** — дописанные туда юнит-тесты
   молча не запускались («no tests to run»). Юнит-тесты — в отдельный файл без тега.
2. **Категории белого списка ограничены** четырьмя: `ticketing`, `afisha`, `gov`, `social`.
   `venue` отвергается с 422.
3. **Админская очередь модерации не показывает `draft`** — `listEvents` принимает только
   `published`, `rejected`, `pending_review`. Пять прошедших телеграм-черновиков не видны
   в админке нигде, и это не баг очереди, а её контракт.
4. **Счётчик вкладки «На проверке» врёт нулём** до первого клика: `linksCount` в
   `frontend/components/AdminModeration.tsx:97` инициализируется нулём и заполняется
   только внутри ветки `filter === "links"`. Очередь из трёх событий выглядела пустой.
   **Не исправлено.**
5. Расширение браузера может открыть окно в другом профиле Chrome — сессия там своя,
   `localStorage` пуст.
